### 覆盖率 ≥70%

```bash
cd backend
pytest --cov=app --cov-report=term-missing --cov-fail-under=70
# 或从仓库根目录：make test-cov
```

**实测（2026-10-04，本机）**：`pytest -m 'not model'` = **616 passed / 2 skipped / 10 deselected**；
覆盖率 **77%**（8407 条语句 / 未覆盖 1942），`coverage report --fail-under=70` 通过。
门槛写在 `backend/pyproject.toml` 的 `[tool.coverage.report] fail_under = 70`，
**不达标直接非零退出**，所以"覆盖率达标"这件事是可验证的而不是自述的。

未覆盖的重灾区（想再抬覆盖率从这里下手，按收益排序）：
`app/db/init_db.py`（一次性建库脚本，0%）、`app/indexing/pipeline.py`（16.7%）、
`app/api/v1/graph.py`（20.6%，图分析逻辑本身已被 `test_graph_analysis.py` 覆盖，
薄的是 HTTP 层）、`app/workers/scheduler.py`（25.5%）。

> 本机跑之前先看一眼 `PITFALLS.md`「环境 / 工具链」：
> ① 用隔离 venv（`C:/tmp/rcvenv`）；
> ② 把覆盖率数据写到仓库外 `COVERAGE_FILE=C:/tmp/rc.coverage`；
> ③ **换一个新会话跑** —— coverage 收尾要删 `.coverage.<host>.<pid>` 这批并行数据文件，
> 同一个会话里累计删除数一过 50，就会被批量删除守卫拦成 `INTERNALERROR`
> （**测试其实全绿**，日志里 `==== 616 passed` 与 `file_be_gone` 同时出现就是这个坑）。
> 绕不过去时的备选：`coverage run --source=app -m pytest` + `coverage report --fail-under=70`
> （单进程、不产生并行数据文件，因此不需要删除）。

### 前端 E2E（Playwright）

```bash
cd frontend
npm run e2e:install     # 首次：下载 chromium（约 300MB）
npm run e2e             # 跑关键流程；dev server 没起会自动拉起，起了就复用
npm run e2e:headed      # 看着浏览器跑

```

覆盖：营销站三页渲染与标题、工作台六个模块入口、顶栏后端健康徽章可交互、
兜底 404 返回真 404。**全部不依赖后端** —— 后端没起时页面必须显示状态徽章而不是白屏，
这条行为本身就要守住。每条用例都会断言「没有未捕获的 JS 异常」，
用来兜住 typecheck / build / SSR 全绿但客户端 hydration 炸掉的那类问题。

**实测（2026-10-04，本机，复用已起的 dev server）**：**10 passed / 37.9s**。
跑之前注意两点：
① 用 `channel: 'chromium'`（完整浏览器 + 新无头模式）而不是 Playwright 默认的 headless shell
—— shell 是裁过的构建，截图与渲染跟真人看到的不一样，而这一层要看的正是"人看到的东西"；
② dev server 若已在 3000 端口，配置会自动复用（`reuseExistingServer: true`），
**别在它跑着的时候 `nuxi build`**（构建要清 `.nuxt`）。

## 五、部署

### 日常形态（开发）

```bash
make up          # → 前端 :3000，后端 :8000/docs
```

### 生产形态（含 Nginx 反向代理）

```bash
make up-prod     # = docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
# → 统一入口 http://<host>/ （前端 / API / MCP 都在 80 上）
```

生产覆盖层相对基础文件只改四件事：

1. **数据服务 + 应用服务全部 `restart: always`** —— 24h 演示要求进程自愈；
2. **backend 摘掉代码热更新挂载与 `--reload`**，改多 worker，日志落到 `./logs/backend/`；
3. **frontend 的 API 基址改成同源相对路径 `/api/v1`** —— 走 Nginx 就不再跨域；
4. **加 Nginx 服务**（SSE 关缓冲、200MB 上传上限、MCP 透传、SPA 兜底）。

日志有两层：容器 stdout 走 json-file 轮转（20MB × 5），后端生产模式另外写
`./logs/backend/app.json`（loguru 结构化、按天轮转、保留 14 天），Nginx 访问日志写
`./logs/nginx/access.log`（JSON 格式）。

### GPU 形态（可选，需 nvidia-container-toolkit）

```bash
make up-gpu      # 叠加 docker-compose.gpu.yml：backend 用 cuda，Milvus 换 -gpu 镜像
```

> ⚠ 本机 `nvidia-smi` 报 `Failed to initialize NVML`（无可用 GPU），所以 **GPU 层只做了
> YAML 结构校验（`docker compose config` 通过），未在真卡上跑过**。上真卡后请复验：
> `docker compose exec backend python -c "import torch;print(torch.cuda.is_available())"`

### HTTPS

见 **`deploy/HTTPS.md`**：证书来源三种做法、certbot webroot 签发与续期命令、
打开 HTTPS 的三处改动、上线后五条自检命令、六个常见坑。默认只监听 80
（缺证书时 Nginx 起不来会直接违背「24h 可用」，所以 HTTPS 做成显式开关）。

### 评审访问门禁（“评审专用账号”）

系统**没有登录体系**，所以评审账号落在网关层最省：一段 Nginx Basic Auth。

```bash
docker run --rm httpd:2.4-alpine htpasswd -nbB reviewer '你的密码' > deploy/nginx/htpasswd
```

然后打开 `deploy/nginx/research-copilot.conf` 里「评审访问门禁」那三行注释，
并在 `docker-compose.prod.yml` 的 nginx.volumes 挂上 `htpasswd`。
`/healthz` 必须放行，否则 compose 会把 Nginx 判死。

> 如果赛事**不要求**门禁，不要开 —— 多一道凭据就多一个发不出去链接的风险。

### 24h 保活清单

| 项 | 措施 |
|---|---|
| 进程自愈 | 所有服务 `restart: always` |
| 探活 | 数据服务 5 个 healthcheck + backend `/health` + Nginx `/healthz`（独立于后端） |
| 依赖顺序 | backend `depends_on: service_healthy`，不会在 Milvus 没起来时抢跑 |
| 磁盘 | 容器日志轮转 + loguru 14 天保留 + `docker system df` 定期看 |
| 数据 | 5 个命名卷 + `models_cache` 卷（重建镜像不重下 bge-m3） |
| 入口 | Nginx 单入口 80，`client_max_body_size 200m` 支持大 PDF |
| 上线后 | `python scripts/preflight.py --url https://<域名>` |
