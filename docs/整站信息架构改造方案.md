# 整站信息架构改造方案

> 目标：参考 `ponder.ing/zh` 的**多路由信息架构与视觉风格**改造现有项目。
> 原则：**改造，不重写**。保留业务逻辑 / API / 状态管理 / 表单校验，只动 UI 层。
> 状态：**方案待确认，尚未写任何实现代码。**

---

## 0. 结论摘要

三句话：

1. **现状比预期窄**：现有前端只有 **1 个路由**（`/`，即那套三栏工作台），没有 `layouts/`、没有 `error.vue`、没有 `public/`、没有品牌资产。所以"路由映射"里 **1 条是迁移、14 条是新增**（合计 15 条）—— 这是"建营销站"，不是"改路由"。
2. **参考站比预期重**：`ponder.ing` 的中文站有 **275 个 URL**（实测 `sitemap-zh.xml`），其中绝大多数是 SEO 博客/功能落地页，真正的产品界面只有 `/dashboard` 一个，而且被 `robots.txt` 主动屏蔽。**不要按它的规模抄它的 IA。**
3. **有两个硬依赖不在 UI 层**：`登录/注册` 需要后端先有用户体系（**当前完全没有**）；`博客/定价` 需要内容源（**当前完全没有**）。这两块无法靠"只改 UI"完成，必须先做取舍决策（见 §8）。

## 1. 现状盘点（全部实测）

### 1.1 前端

| 项 | 实测值 |
|:--|:--|
| 路由 | **1 个**：`/` → `pages/index.vue`（125 行，三栏工作台） |
| `layouts/` | **不存在** |
| `error.vue` | **不存在**（404/500 走 Nuxt 默认页） |
| `app.vue` | 只有 `<NuxtPage />`（7 行） |
| 组件 | 18 个顶层 + 6 个 `ui/` = **24 个** |
| Store | 5 个（library / selection / graph / chat / ui） |
| Composable | 3 个（useApi / useChatStream / useMarkdown） |
| 静态资源 | **无 `public/` 目录**，`assets/` 下只有 `main.css` |
| 样式 | Tailwind v4，token 全在 `assets/css/main.css` 的 `@theme` |
| `routeRules` | `{ '/': { ssr: true } }` |
| 依赖 | Nuxt 3.15 / Pinia / ECharts / pdfjs-dist / markdown-it / dompurify / Phosphor —— **无 UI 框架** |

关键配置（`nuxt.config.ts`）：

```ts
components: [{ path: '~/components', pathPrefix: false }]
```

`pathPrefix: false` 意味着 `components/` 下**所有**组件都进全局自动导入命名空间。加 30 个营销组件会让全局命名污染，见 §7 R4。

### 1.2 后端

| 项 | 实测值 |
|:--|:--|
| 已注册路由 | 7 个：`papers` / `qa` / `chat` / `graph` / `writing` / `tools` / `tasks` |
| 统一响应体 | `{code, data, message}`（`ApiResponse`） |
| 鉴权路由 | **不存在**（无 `auth.py`，无 `/auth/*`） |
| `User` 模型 | **不存在**（`models/` 只有 paper / chunk / citation / conversation / task） |
| `current_user` 依赖 | **不存在**（`api/deps.py` 只有 `SessionDep` / `PageDep`） |
| JWT/bcrypt 工具 | **存在但未接线**：`core/security.py` 有 `hash_password` / `verify_password` / `create_access_token` / `decode_access_token` |
| 内容类接口 | **不存在**（无 blog / post / pricing / plan） |

> ⚠️ **这是本方案最关键的发现**：需求里写"保留鉴权"，但项目**目前没有鉴权**。
> `security.py` 提供的是"零件"，没有装配到任何路由上；前端 `useApi.ts` 也不注入 `Authorization` 头。
> 所以 `/login`、`/signup` 属于**新增功能**，不是 UI 改造。

## 2. 参考站真实 IA（实测，非推测）

拉取 `robots.txt` + `sitemap.xml` + `sitemap-zh.xml` + 首页原始 HTML 得到：

**顶层路径（中文站）**

| 路径 | 性质 |
|:--|:--|
| `/zh` | 营销首页 |
| `/zh/features` + `/zh/features/[slug]` | 功能落地页（SEO） |
| `/zh/pricing` | 定价 |
| `/zh/blog` + `/zh/blog/[slug]` | 博客（**数百篇 SEO 文章**） |
| `/zh/help` | 帮助中心 |
| `/zh/release-notes` | 更新日志 |
| `/zh/dashboard` | **真正的产品界面** |
| `/zh/user/signup` | 注册 |
| `/agreements/service.html`、`/agreements/privacy.html` | 法律条款（静态 html） |

**规模与结构**

- 中文站 **275 个 URL**；站点共 **10 个语言**（en / zh / zh_hant / ko / ja / pt / es / fr / de / tr）
- 无 `/about` 页面（站内 "about" 只出现在正文里）
- `/login` 不在 sitemap 中

**`robots.txt` 屏蔽了应用区**：

```
Disallow: /*/user      Disallow: /user
Disallow: /*/flow      Disallow: /flow
Disallow: /*/subscription   Disallow: /subscription
Disallow: /*/ponder    Disallow: /ponder        ← 工作台
Disallow: /*/space     Disallow: /space
Disallow: */payment-result
```

**可提取的导航/页脚链接**（`href` 实测）：

```
/zh           /zh/features    /zh/blog      /zh/pricing
/zh/help      /zh/release-notes
/zh/dashboard /zh/user/signup
/agreements/privacy.html       /agreements/service.html
```

### 2.1 从这个结构里该学什么、不该学什么

| 该学 | 不该学 |
|:--|:--|
| **营销层与应用层物理分离**（`/` 公开，`/dashboard` 需登录且 noindex） | 数百篇 SEO 博客的规模 —— 我们没有内容运营团队 |
| SSG/SSR 优先给营销页，应用页单独 `routeRules` | 10 语言 i18n —— 本项目只面向中文单语 |
| 吸顶导航 + 汉堡菜单 + 卡片悬停 + 滚动入场的**交互模式** | 营销站的视觉密度（大留白、大字），直接搬进工作台会毁掉信息密度 |
| `/features/[slug]` 这种"功能点独立成页"的可扩展结构 | 直接把 `/` 改成营销页而不给工作台留新家 |

## 3. 现有路由 → 目标路由映射表

### 3.1 迁移（唯一一条）

| 现状 | 目标 | 动作 | 代码改动 |
|:--|:--|:--|:--|
| `/` → `pages/index.vue`（三栏工作台，125 行） | `/app` → `pages/app/index.vue` | **搬移文件，内容零改动** | 仅 `definePageMeta` 加 `noindex` |

> 工作台的 `mainView`（阅读器 / 引文图谱切换）**继续保持站内状态**（走 `ui.layout.mainView`），**不拆成路由**。
> 理由沿用上轮已确认的结论：最高频动作是"读原文 → 就这段提问"，跳路由会丢滚动位置、划词与选中文献。

### 3.2 新增（14 条路由，分 3 层）

**A. 营销层**（公开 / SSR / 可索引）

| 路由 | 页面 | 内容源 | 优先级 |
|:--|:--|:--|:--|
| `/` | 首页（Hero / 功能 / 场景 / 评价 / FAQ / CTA） | 静态 | **P0** |
| `/features` | 功能总览 | 静态 | P1 |
| `/features/[slug]` | 功能详情 | 静态 md | P2 |
| `/pricing` | 定价 | 静态配置（**暂不接支付**） | **P0** |
| `/blog` | 博客列表 | 静态 md / CMS | P1 |
| `/blog/[slug]` | 博客详情 | 同上 | P1 |
| `/about` | 关于 | 静态 | P1 |
| `/help` | 帮助中心 | 静态 md | P2 |
| `/changelog` | 更新日志 | 可选 | P3 |
| `/legal/terms`、`/legal/privacy` | 法律条款 | 静态 | P1 |

**B. 鉴权层**（公开 / **强依赖后端新增 auth**）

| 路由 | 页面 | 阻塞条件 |
|:--|:--|:--|
| `/login` | 登录 | 后端 `/auth/login` + `User` 模型 + 迁移 |
| `/signup` | 注册 | 后端 `/auth/register` |
| `/reset-password` | 找回密码 | 邮件通道（可延后） |

**C. 应用层**（需登录 / noindex）

| 路由 | 页面 | 数据源 |
|:--|:--|:--|
| `/app` | 工作台（原 `/` 的内容） | 现有 7 个 API，**零改动** |

**D. 错误**

| 文件 | 覆盖 | 动作 |
|:--|:--|:--|
| `error.vue` | 404 / 500 | 新增（品牌化版 Nuxt 默认错误页） |

### 3.3 布局壳规划

| 文件 | 用于 | 内部结构 |
|:--|:--|:--|
| `layouts/marketing.vue` | 上述 A / B 层 | `MarketingHeader`(吸顶) + `<slot/>` + `MarketingFooter` |
| `layouts/minimal.vue` | `/login`、`/signup`、`error.vue` | 只放居中容器 + 小 logo，无导航干扰 |

> **工作台不套 layout。** `pages/app/index.vue` 自己就是壳（`AppTopBar` + 三栏 + `AppStatusBar`）。
> 把它抽成 layout 是纯粹的搬箱子，会引入回归风险而零收益。**保持原样。**

### 3.4 `routeRules` 目标

```ts
routeRules: {
  '/':          { ssr: true },   // 营销首页
  '/blog/**':   { ssr: true },   // 博客需要爬虫看到全文
  '/features/**': { ssr: true },
  '/pricing':   { ssr: true },
  '/legal/**':  { ssr: true },
  '/app/**':    { ssr: true },   // ← 保持现状！不改成 ssr:false
}
```

> `/app/**` **维持 `ssr: true`**。现在工作台骨架是 SSR 出来的（首屏不白屏），改成纯 CSR 是**功能退化**。
> 不被搜索引擎收录用 `<meta name="robots" content="noindex">` 解决，不用关 SSR。

## 4. 设计 token 建议

### 4.1 现在有什么

`assets/css/main.css` 的 `@theme` 已经是从 `ponder.ing` 实测 computed style 抄来的，**视觉基调本身就是参考站**：

| 类别 | 现有 token |
|:--|:--|
| 底色 | `--color-canvas #f7f7f8`、`--color-surface #fff`、`--color-sunken`、`--color-hover`、`--color-active` |
| 墨色 | `--color-ink #0f161e`、`ink-2`、`ink-3`、`ink-4` |
| 发丝线 | `--color-hairline rgb(15 22 30 / .08)`、`--color-hairline-2` |
| 强调色 | `--color-brand #805ce5`（**唯一彩色**）、`--color-brand-ink`、`--color-brand-soft`、`--color-brand-ring` |
| 语义色 | `--color-ok/warn/bad` + `-soft` |
| 圆角 | `--radius-xs 4` → `--radius-2xl 32` |
| 阴影 | `--shadow-xs` → `--shadow-lg` |
| 字号 | `--text-2xs 11px`（唯一自定义文本 token） |
| 字体 | `--font-sans`（Inter + Noto Sans SC）、`--font-mono` |

**结论：颜色、圆角、阴影、字体都不用动。** 缺的只有"营销页尺度"。

### 4.2 需要新增（**只增不改**）

```css
@theme {
  /* 展示级字号阶梯 —— 营销页专用，工作台完全不受影响 */
  --text-display-xl: 56px;  --text-display-xl--line-height: 1.14;  --text-display-xl--letter-spacing: -0.03em;  --text-display-xl--font-weight: 600;
  --text-display-l:  44px;  --text-display-l--line-height: 1.18;   --text-display-l--letter-spacing: -0.02em;   --text-display-l--font-weight: 600;
  --text-display-m:  32px;  --text-display-m--line-height: 1.25;   --text-display-m--letter-spacing: -0.015em;  --text-display-m--font-weight: 600;
  --text-section:    24px;  --text-section--line-height: 1.3;
  --text-lead:       17px;  --text-lead--line-height: 1.65;

  /* 容器宽度：营销页正文与页面栅格 */
  --container-page:  1200px;
  --container-prose: 68ch;
}
```

```css
/* 动效时序放普通 CSS 变量，不放 @theme —— 避免依赖不确定的命名空间映射 */
@layer base {
  :root {
    --ease-out-soft: cubic-bezier(0.22, 1, 0.36, 1);
    --dur-fast: 140ms;   /* 悬停 / 焦点 */
    --dur-base: 220ms;   /* 标签切换 / 折叠 */
    --dur-reveal: 520ms; /* 滚动入场 */
  }

  @media (prefers-reduced-motion: reduce) {
    :root { --dur-fast: 0ms; --dur-base: 0ms; --dur-reveal: 0ms; }
  }
}
```

### 4.3 三条必须守住的约束

1. **只增不改。** `--text-2xs: 11px`、body `13.5px`、`--radius-*`、所有 `--color-*` 一律冻结。
   工作台的信息密度是调出来的，改任何一个值整站视觉会漂。这条建议用截图 diff 机械守住（见 §7 R6）。
2. **仍然只有一种彩色。** 营销页需要视觉张力时，用 `--color-brand` 实底 + 白字，或 `--color-brand-soft` 浅底 + `--color-brand-ink` 文字。
   **不要引入第二种彩色** —— 现有 token 注释里已经把这条写成原则了。
3. **维持 light-only。** 参考站本身也是 light-only。若营销页想加"深色 CTA 区块"，那需要**另起一整套**反色 token（8% 黑发丝线在深底上完全失效），不是一个 section 的事。

### 4.4 字号尺度对照（避免营销页污染工作台）

| 用途 | 工作台（现状） | 营销页（新增） |
|:--|:--|:--|
| 正文 | `13.5px / 1.6` | `--text-lead` 17px / 1.65 |
| 辅助 | `--text-2xs` 11px | 14px |
| 区块标题 | `text-base` ~15px | `--text-section` 24px |
| 页面主标题 | 无 | `--text-display-l` 44px |
| Hero | 无 | `--text-display-xl` 56px |

### 5.4 组件命名隔离（**必须做**）

现在 `pathPrefix: false` 会让 `components/**` 全部进全局。新增 30 个组件后：

- `Section` / `Container` / `Hero` 这种名字**极易与 HTML 元素或未来组件冲突**
- 营销组件里出现 `<Section>` 时，排查"这是谁的 Section"会变成常态

建议加一条配置，把营销组件收进独立前缀：

```ts
components: [
  { path: '~/components',            pathPrefix: false },   // 工作台保持原样
  { path: '~/components/marketing',  pathPrefix: true  },   // → <MarketingHero>
  { path: '~/components/auth',       pathPrefix: true  },   // → <AuthLoginForm>
]
```

这样工作台模板**一个字符都不用改**，营销层则得到显式命名空间。

### 5.5 博客正文渲染的复用判断

现有 `useMarkdown.ts` 已具备：markdown-it（`html: false`）+ DOMPurify + MathJax 重排。
博客正文**可以复用这条管线**，但要注意：

- 博客正文**不需要** `decorateCitations` / `typesetMath`（那是给 LLM 回答用的）
- 需要新增的是：标题锚点 id（给 TOC 用）、外链 `target="_blank" rel="noopener"`、图片懒加载
- 内容来源二选一：
  - **A. `@nuxt/content`**（Nuxt 官方方案，md 文件 + front-matter，自带查询/SSR/热更新）
  - **B. 手写 `content/blog/*.md` + `import.meta.glob`**（零新依赖，但要自己写 front-matter 解析与分页）

> 建议 **A**。博客列表/详情/分页/标签/SEO 是 Nuxt Content 的成熟场景，自己写约等于重造。这是本方案唯一建议新增的重依赖。

## 6. 分阶段改造步骤

每阶段都有**独立验收**，可单独停下来。

### 阶段 0 — 前置决策（不写码）

产出：本方案确认 + 四个决策（§8）拍板。

- [ ] 品牌资产是否具备（logo / 主视觉 / 截图）
- [ ] 博客内容源：Nuxt Content / 手写 glob / 外部 CMS
- [ ] 鉴权是否纳入本轮（决定 `/login`、`/signup` 是否进阶段 6）
- [ ] 定价页是否需要真实支付（建议：本轮的定价页**纯展示**，不接支付）

### 阶段 1 — 路由壳与布局骨架（**不碰工作台**）

- 新建 `pages/app/index.vue`：从 `pages/index.vue` **原样搬移**，仅加 `noindex`
- 新建 `layouts/marketing.vue`、`layouts/minimal.vue`（先只有结构，无样式细节）
- 新建 `error.vue`
- `pages/index.vue` 先放一个占位首页（后续阶段替换）
- 更新 `routeRules`

**验收**：访问 `/app`，三栏工作台与改造前**逐像素一致**；`/` 不再 404。

### 阶段 2 — 设计 token 与动效基座

- §4.2 的 token 追加进 `@theme` + `@layer base`
- `RevealOnScroll` 组件（含 `prefers-reduced-motion` 短路）
- 组件命名隔离配置（§5.4）

**验收**：`/app` 截图与阶段 1 **零差异**（token 只增不改的机械证明）。

### 阶段 3 — 营销外壳

- `MarketingHeader`：吸顶（滚动 > 8px 加发丝线 + 背景模糊）、移动端汉堡菜单、当前路由高亮
- `MarketingFooter`：分组链接 + 版权 + 法律入口
- 键盘可达性：菜单按钮 `<button>`、Esc 关闭、`aria-expanded`

**验收**：375 / 768 / 1024 / 1440 四档宽度下导航不溢出；Tab 键可完整走完菜单。

### 阶段 4 — 首页 / 定价 / 关于

- 首页：Hero → LogoCloud → FeatureGrid → HowItWorks → TestimonialCarousel → FAQAccordion → CTABand
- 定价：PricingTable + FAQ（**纯展示，无支付**）
- 关于：TeamGrid + Timeline

**验收**：Lighthouse 性能 ≥ 90、可访问性 ≥ 95。

### 阶段 5 — 博客

- Nuxt Content 接入 + `content/blog/` 目录
- `/blog` 列表（分页 + 标签筛选）、`/blog/[slug]` 详情（TOC + 上一篇/下一篇）

**验收**：`curl` 拿到的 HTML 里**含完整正文**（证明 SSR 生效，不是客户端渲染的空壳）。

### 阶段 6 — 鉴权页（**仅当后端 auth 就绪**）

## 7. 风险点

### R0 ⛔ 阻塞级：`renderMarkdown` 在服务端会抛异常（**已实测确认**）

`composables/useMarkdown.ts` 的注释写着 `render()` 是"纯函数，SSR 安全"，但实测：

```
typeof default export = function
has .sanitize ?        undefined
isSupported ?          false
sanitize() 抛错: TypeError - createDOMPurify.sanitize is not a function
```

`dompurify` 的默认导出**在无 DOM 环境下是工厂函数**，`isSupported === false`，没有 `.sanitize` 方法。
即 `renderMarkdown()` 一在服务端被调用就抛 `TypeError`。

**为什么现在没暴露**：工作台首屏没有聊天消息，`renderMarkdown` 在 SSR 期间从未真正执行。
**为什么博客会引爆**：博客详情页每次请求都要在服务端渲染正文 → **每个请求 500**。

**最小修复**（二选一）：

```ts
// 方案一：只在客户端净化（推荐）
import createDOMPurify from 'dompurify'
const purify = typeof window === 'undefined' ? null : createDOMPurify

export function renderMarkdown(source: string): string {
  const html = md.render(source || '')
  return purify ? purify.sanitize(html, { ADD_ATTR: ['data-marker'] }) : html
}
```

```ts
// 方案二：换成 isomorphic-dompurify（代价：引入 jsdom，包体积显著变大）
```

补充实测结论作为佐证：`markdown-it` 配置 `html: false` 时裸 HTML 已被转义 ——
输入 `<script>alert(1)</script>` 得到的是 `&lt;script&gt;alert(1)&lt;/script&gt;`，
`<img src=x onerror=...>` 也整体被转义成纯文本。
所以**方案一是安全的**：服务端不净化不会开 XSS 口子，净化本属纵深防御。

> 这个修复应作为**阶段 2 的附带项**先落地，否则阶段 5 一定卡住。

### R1 ⛔ 高：鉴权不存在，`/login`、`/signup` 超出"只改 UI"范围

需求写"保留鉴权"，实际是"**从零建鉴权**"。涉及：数据模型 + 迁移 + 4 个接口 + token 存储 + 请求头注入 + 路由守卫 + 表单校验。这是完整功能开发，建议**独立排期**，不要塞进本次 UI 改造里被拖累。

**如果本轮不想做后端**：把 `/login`、`/signup` 从阶段 6 移除，只在 UI 上留入口。

### R2 高：博客与定价没有数据源

参考站有 275 个 URL，我们一个都没有。三个选择：

| 方案 | 代价 |
|:--|:--|
| 静态 markdown（Nuxt Content） | 需写内容；迁移/发布要重新构建 |
| 外部 CMS | 引入外部依赖 + 网络调用 |
| 后端新增内容接口 | 后端工作量 + 管理端 |

**定价页尤其要划线**：参考站的 `robots.txt` 里有 `/subscription`、`/payment-result`，说明它接了支付。
**支付涉及合规、对账、退款，绝不是 UI 改造的内容。** 本轮建议定价页纯展示。

### R3 中：SSR 与 `ClientOnly` 的取舍要分路由处理

`routeRules` 必须按路由区分：营销页 SSR（SEO 必需），`/app/**` 保持现有 SSR 行为。
**不能全局设 `ssr: false`**（营销页就没 SEO 了），也**不能把 `/app` 改成 `ssr: false`**（首屏骨架会丢）。

### R4 中：全局自动导入的命名污染

`pathPrefix: false` + 30 个新组件 = `Section` / `Hero` / `Container` 这类通用名进入全局。
用 §5.4 的目录隔离方案处理。**这是新增组件前的必做项**，事后重构代价高得多。

### R5 中：Tailwind 类名静态扫描（**上轮已踩过**）

营销页会有大量 `hover:` / `group-hover:` / `md:` 变体，动态拼类名（`bg-${tone}`）在生产构建会被 purge。
沿用现有约定：**变体类名一律在 `utils/ui.ts` 写字面量**，不拼字符串。

### R6 中：工作台视觉回归

token "只增不改"必须机械守住。建议轻量做法：阶段 1、2 各截一次 `/app` 的三档宽度截图做像素对比。
上一轮的截图脚本可直接复用。

### R7 中：品牌资产缺失

要求 3 说"品牌、Logo、图片用我们的"——但项目**没有 `public/`、没有任何图片资源**。
需要你提供 logo（SVG 优先）与至少 1 张产品截图；没有的话先用文字标 + Phosphor 图标占位。

### R8 中：移动端是两件事，别混在一个阶段

- **营销页移动端化**：常规响应式，阶段 3–7 覆盖
- **工作台移动端化**：三栏假设 ≥1024px，要改抽屉/标签。这属于**独立工程**，不要顺手做

### R9 低：动效别溢进工作台

滚动入场、轮播、卡片悬停是营销站的语言。
**在数据密集的工作台里它们是噪音**（每滚动一次就闪一次）。动效只加在 `marketing` / `auth` 层。

### R10 低：i18n 现在不做，但结构留口

参考站有 10 种语言。本项目中文单语，本轮**不做 i18n**（YAGNI）。
但路由设计上避免硬编码，将来接 `@nuxtjs/i18n` 走前缀模式时不用重排目录。
